PRJ-01 Complete

Multi-Node ESP32 Mesh Network with Wireless OTA Updates

Embedded Wireless Firmware

A 3-node ESP32 mesh where remote sensor nodes report data wirelessly to a gateway over ESP-NOW, and the gateway can push firmware updates over the air — with automatic rollback if the new firmware is broken. The rollback path is the actual hard problem here: any network can move data, but a safe OTA system has to assume the new code might fail and recover on its own, with zero physical access.

Read full writeup

Sensor data moves over ESP-NOW, a lightweight connectionless protocol built into every ESP32, chosen because nodes don't need to stay associated with a WiFi network just to report routine readings. Firmware updates are pulled by the node over standard WiFi + HTTP instead — simpler and more reliable than chunking a large binary over ESP-NOW's small packet size. The gateway coordinates the network: it relays sensor readings to serial output and broadcasts "new firmware available at this URL" on command. The binary itself is hosted by a laptop's Python HTTP server on the same network, sidestepping the need to write to the ESP32's own flash filesystem at this stage.

GatewayESP32 Dev Module — coordinates the network, no sensor attached Node 1ESP32 Dev Module + DHT11 temp/humidity sensor Node 2ESP32 Dev Module — simulated readings in software

How the rollback actually works: the ESP32 bootloader keeps firmware in two separate flash partitions. A new OTA image is written to the inactive partition while the device keeps running normally off the current one. Only after the new image passes a checksum does the bootloader switch over and try booting it — and if that firmware crashes or never confirms it's healthy, the bootloader reverts to the last working partition automatically.

To confirm this wasn't just true in theory, three firmware versions were pushed in sequence: v1 (baseline, flashed via USB), v2 (adds a marker to serial output — pushed via OTA successfully), and v3, which deliberately calls abort() on boot. Pushing v3 triggered the exact failure path it was designed to test: the device automatically rolled back to v2 with no manual intervention.

Possible extensions:

  • MQTT publishing from the gateway to a Node-RED / Grafana dashboard
  • Signed firmware binaries, verified before flashing, for secure OTA
  • Move firmware hosting onto the gateway's own flash (LittleFS), removing the laptop dependency
  • Chunk firmware transfer over raw ESP-NOW for nodes that should never join WiFi
PRJ-02 Complete

Ultrasonic Sensor Accuracy & Noise Characterization

Sensors Data Analysis Python

Bench-tested an HC-SR04 ultrasonic sensor to find out how much to actually trust its readings — logging distance data over serial across a 5–30 cm range and computing error, noise, and drift against known reference distances. Live data below — hover the points.

Read full writeup

Method: an HC-SR04 was wired to an Arduino Uno R3 and triggered continuously; each reading was timestamped and streamed over serial to a Python script that logged to CSV and computed summary statistics. A flat target was placed at six known distances (5–30 cm) for an accuracy sweep, and left untouched at 20 cm for 5 minutes (2,997 samples) to check for drift.

Stability (20 cm, 5 min)Mean 19.17 cm · Noise σ 0.006 cm · Drift −0.0002 cm/min

Findings: error wasn't constant in direction. At short range (5–10 cm) the sensor read slightly high (+0.17 to +0.37 cm); starting around 15 cm that flipped to reading low, growing to −1.00 cm at 30 cm — a distance-dependent bias, not a fixed offset.

Noise told a different story: extremely low and flat from 5–15 cm (0.006–0.010 cm), then a 30–50x jump at 20 cm that stayed elevated through 30 cm — a distinct reliability transition rather than a smooth increase. Oddly, the separate 5-minute stability test at 20 cm showed noise of just 0.006 cm — 50x lower than the same distance in the accuracy sweep. Since the distance was identical, the likely explanation is test protocol, not the sensor: the target may not have been perfectly re-aligned between repositions in the sweep, or the 10-second sampling window was too short to average out multipath effects that a 5-minute window smooths over. That mismatch is itself a useful result — it points to the sensor's true noise floor being closer to 0.006 cm.

Next steps:

  • Re-run the 20–30 cm points with a fixed jig to isolate alignment from sensor noise
  • Extend sampling windows from 10s to ~60s per accuracy point
  • Pinpoint the exact 15–20 cm transition where error sign and noise both shift
  • Test angle-of-incidence sensitivity, and repeat on a second HC-SR04 unit
PRJ-03 Complete

1965 Thunderbird Taillight Controller — Moore FSM on FPGA

Digital Design SystemVerilog FPGA

An 8-state Moore machine in SystemVerilog that reproduces the sequential taillights of a 1965 Ford Thunderbird — left/right turn signals, brake, and hazard — with a strict priority order for when multiple inputs are active at once, synthesized and run live on an FPGA.

Read full writeup

Course lab for UCSB ECE 152A (Digital Design). The spec called for six LEDs per side that light up one at a time in the turn direction, then reset — modeled as an 8-state Moore machine (S000_000 through S111_111) clocked on a 1Hz square wave from a function generator, with an active-low async reset.

The real design problem wasn't the sequencing — it was precedence. Turn signals, brake, and hazard can all be triggered at once, and the spec required a strict override order: hazards beat everything, including both turn signals firing together; brake overrides hazard; a single active turn signal overrides only its own side of the brake lights. That priority logic lives entirely in the FSM's always_comb block ahead of the turn-signal case statements, so hazard/both-turns conditions get checked and short-circuit before turn logic ever runs.

FSM8-state Moore machine, SystemVerilog, priority-encoded transitions HardwareUCSB DigiLab FPGA, 6 through-hole LEDs, function generator for the 1Hz clock

Verified by driving each input combination and confirming the LED pattern against the truth table before demo — including the ambiguous cases (turn signal + brake, both turn signals at once) where the wrong precedence order would show up immediately as the wrong LEDs lighting.

Automatic Night Light

Embedded Analog

An automated nightlight built around an Arduino, a photoresistor (LDR), and an LED circuit — real-time ambient light monitoring in C++ that reads the analog LDR input and dynamically drives the LED output as the room gets darker or brighter.

Read full writeup

Built and programmed within the Arduino IDE, using the photoresistor's analog signal to decide, in real time, whether the LED circuit should be on or off. Debugging leaned heavily on the Serial Monitor — watching raw sensor values live to catch wiring issues and tune the light threshold, rather than guessing at the right cutoff.
